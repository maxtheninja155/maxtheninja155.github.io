Overview

Backyard Volley is a first-person, online 2v2 grass volleyball game for Steam (Windows), built solo in a six-week sprint under (The) Ninja Production. The defining mechanic: the player's mouse is their arm. Every hit — spike, tip, bump, set, block, serve — is performed by physically flicking the mouse. There are no context buttons and no hit-selection menus; the game derives intent from the player's state at the moment of ball contact — airborne or grounded, button held or not, look angle.

Tonally it's deliberately low-stakes and high-energy, designed for a four-person Discord call where failure is funny rather than frustrating. Underneath that silliness, one person designed and built a novel input mechanic, custom low-latency multiplayer netcode, a full AI teammate system, procedural animation, in-editor telemetry tooling, and a tutorial system — under a hard self-imposed deadline with formal milestone gates, hitting every gate on schedule.

A note on the visuals: the character model and court are intentionally minimal. This was a deliberate scope decision — the art pass was the last week's work, and the project is first and foremost a systems-and-feel showcase. What you're looking at is the engineering, with the paint still drying.

Headline Systems

Custom Ball Netcode — “the ball is five numbers”

The standard approach (replicate a rigidbody via snapshot interpolation) put a 200–300ms visible delay on the hitter's own touches. So I deleted the physics engine from the ball: it's kinematic, and its position is a pure closed-form function of five networked values, evaluated identically on every client every frame. Prediction with nothing to reconcile, and bounces solved as math.

The Input System — “your mouse is your arm”

Swing strength is measured in camera-rotation degrees per second, not mouse pixels, so DPI doesn't change the game. A per-player adaptive calibration fits the skill curve to gentle and aggressive flickers alike, and the power formula composes three independent skill axes — flick intensity, flick timing, and jump-phase timing.

AI Teammates — “four players needed, one available”

A 2v2 game needs four players to test; a solo dev has one. So I built full AI players where a bot is just a second producer of input — one branch, every downstream system shared. Difficulty degrades perception, never buffs physics, and the attack planner runs real projectile math on the deterministic ball.

01 Netcode

The Ball Is Five Numbers

The standard way to network a physics object is to replicate the rigidbody transform via snapshot interpolation. In two-client testing of an earlier NetworkRigidbody3D-based build, that produced a 200–300ms visible delay on the hitter's own touches. In a game whose entire premise is “your mouse is your arm,” lag between your flick and the ball responding kills the product — and snapshot interpolation is behind real-time by design.

The insight: a ball in flight is a parabola. It doesn't need a physics engine — it needs five parameters. So I made the ball kinematic and described its entire trajectory with five [Networked] values that every client evaluates identically.

02 Rendering

Rendering the Parabola at 60+Hz on a 32Hz Sim

Position is a pure function of (startPos, startVel, gravity, elapsed). To bridge the 32Hz network simulation to 60+Hz rendering, I self-rolled a sub-tick interpolator rather than depend on a Fusion API (Runner.LocalAlpha) that isn't stable across SDK versions: I track wall-clock time since the last observed tick advance and derive a [0,1] fraction.

C# Assets/Scripts/Gameplay/Ball.cs · ~L464 
static Vector3 ComputeBallisticPos(Vector3 startPos, Vector3 startVel, float gravity, float elapsedSeconds) {
    if (elapsedSeconds < 0f) elapsedSeconds = 0f;
    return startPos
         + startVel * elapsedSeconds
         + 0.5f * Vector3.down * gravity * elapsedSeconds * elapsedSeconds;
}

// Fractional sim tick at the current render frame. We track Time.time
// at the most-recent observed Runner.Tick advance and derive a [0,1]
// fraction from wall-clock elapsed since then. Gives smooth render-
// rate ball motion (60+Hz) on top of the 32Hz sim.
float CurrentFractionalTick() {
    int currentTick = (int)Runner.Tick;
    if (currentTick != _cachedLastTick) {
        _cachedLastTick      = currentTick;
        _cachedTickStartTime = Time.time;
    }
    float dt      = Runner.DeltaTime;
    float subTick = (Time.time - _cachedTickStartTime) / Mathf.Max(0.0001f, dt);
    if (subTick < 0f) subTick = 0f;
    if (subTick > 1f) subTick = 1f;
    return currentTick + subTick;
}

// ... consumed in LateUpdate(), every render frame on every client:
GetActiveTrajectory(out int startTick, out Vector3 startPos, out Vector3 startVel, out float gravity);
float elapsedTicks = CurrentFractionalTick() - startTick;
float elapsed      = elapsedTicks * Runner.DeltaTime;
Vector3 ballisticPos = ComputeBallisticPos(startPos, startVel, gravity, elapsed);
03 Prediction

Prediction With Nothing to Reconcile

When a non-authority player hits the ball, their client renders the predicted trajectory instantly as a local override — and the RPC to the authority carries the hitter's own start position and start tick. The authority writes those values verbatim. Local prediction and the eventual authoritative state therefore describe the exact same curve from the exact same baseline: when the generation counter acknowledges the hit and the override drops, the rendered position is continuous. No snap, no smoothing pass, no reconciliation error to hide.

C# Assets/Scripts/Gameplay/Ball.cs · ~L558 
public void ApplySpikeImpulse(Vector3 newVelocity, float gravityMultiplier = 1f, float rollAmount = 0f,
                              int originatingSideLayer = -1, NetworkId hitterId = default) {
    // ...
    if (Object != null && Object.IsValid && !HasStateAuthority) {
        int expectedGen  = TrajectoryGeneration + 1;
        int startTick    = (int)Runner.Tick;
        Vector3 startPos = transform.position;
        SetLocalOverride(startPos, newVelocity, gravity, expectedGen, startTick);
        Rpc_ApplySpikeImpulse(newVelocity, gravityMultiplier, rollAmount, originatingSideLayer,
                              startPos, startTick, hitterId);
        return;
    }
    ApplySpikeImpulseAuthoritative(transform.position, (int)Runner.Tick, newVelocity,
                                   gravityMultiplier, rollAmount, originatingSideLayer, hitterId);
}

[Rpc(RpcSources.All, RpcTargets.StateAuthority)]
void Rpc_ApplySpikeImpulse(Vector3 newVelocity, float gravityMultiplier, float rollAmount,
                           int originatingSideLayer, Vector3 hitterStartPos, int hitterStartTick,
                           NetworkId hitterId, RpcInfo info = default) {
    LastHitter = info.Source; // the proxy client that sent the hit = the hitting player
    ApplySpikeImpulseAuthoritative(hitterStartPos, hitterStartTick, newVelocity,
                                   gravityMultiplier, rollAmount, originatingSideLayer, hitterId);
}

// ... in LateUpdate(): drop the override once authority catches up — same parabola, zero snap
if (_hasLocalOverride && TrajectoryGeneration >= _localOverrideGen) {
    _hasLocalOverride = false;
}

Because prediction and authority render the same closed-form parabola from the same tick baseline, added latency delays acknowledgment, not position agreement. The design is latency-tolerant by construction.

04 Collision

Collision Becomes Math

With no physics step, floor bounces are detected analytically: bracket the height crossing across one sim tick, solve the kinematics quadratic for the exact sub-tick contact time (careful root selection — the larger root is the downward crossing because the leading coefficient is negative), and write the reflected trajectory as a fresh authoritative parabola. No tunneling at 32Hz, exact bounce positions, and the bounce replicates everywhere through the same five-value model.

C# Assets/Scripts/Gameplay/Ball.cs · ~L964 
if (currentPos.y > bounceTriggerY && nextPos.y <= bounceTriggerY) {
    // Solve quadratic for exact crossing time of the ball-center plane:
    //   startPos.y + startVel.y*t - 0.5*g*t² = bounceTriggerY
    float a = -0.5f * TrajectoryGravity;
    float b = TrajectoryStartVel.y;
    float c = TrajectoryStartPos.y - bounceTriggerY;
    float disc = b * b - 4f * a * c;
    if (disc < 0f) return;
    float sq = Mathf.Sqrt(disc);
    float t1 = (-b + sq) / (2f * a);
    float t2 = (-b - sq) / (2f * a);
    // Want the downward crossing — the larger positive root (with a < 0).
    float bounceT = Mathf.Max(t1, t2);
    // ...
    Vector3 bounceVel = ComputeBallisticVel(TrajectoryStartVel, TrajectoryGravity, bounceT);
    bounceVel.y = -bounceVel.y;
    bounceVel  *= _bounceRestitution;
    SetAuthoritativeTrajectory(bouncePos, bounceVel, TrajectoryGravity, (int)Runner.Tick);
}

The net is solved the same way: an analytic plane-crossing on the authority, with a 15cm “tape” band that always trickles the ball over and a “body” that reflects it back with heavy velocity loss. A side benefit of the whole model: the ball's flight is deterministic — which is what makes the AI's exact landing prediction possible.

05 Input

Swing Strength in Degrees, Not Pixels

Raw mouse delta is scaled by look sensitivity into what the camera actually rotates — so two players with different mouse DPI produce identical swing values for the same physical motion. Hardware fairness, baked into the unit system. Swing inputs travel as raw per-tick mouse deltas, not a client-computed power scalar, so there's no single “I swung at max power” value to forge; the swing window is rebuilt on the simulating peer from raw input.

The hit impulse RPC does carry the hitter's computed velocity, which the authority accepts verbatim — a deliberate trust-model decision for a friends-only-lobby game (it's what makes the invisible prediction handoff possible), with the per-tick input design keeping the door open for authority-side validation later.

A slow asymmetric EMA (rises fast, falls slowly, persisted across sessions) tracks each player's typical flick intensity, so a gentle flicker and an aggressive flicker both get the full skill curve — same ratios, different absolute numbers.

06 Skill Curve

Three Skill Axes, One Power Formula

The power formula composes three independent skill axes — flick intensity, flick timing, and jump-phase timing — with bonus ceilings deliberately sized so a perfect-everything hit lands exactly on the speed cap. Each hit type then has a designed skill curve, not just different numbers. The standout: the tip inverts the spike's “harder = better” relationship. Tip arc is driven by an AnimationCurve with a hump in the middle, so a soft-to-medium swing produces the perfect dink over a block, while a hard swing flattens into a telegraphed deep ball. The skill is resisting the full-power instinct.

C# Assets/Scripts/Player/VolleyPlayer.cs · ~L2542 
int   peakAge      = (recentIdx - peakIdxInBuffer + windowSize) % windowSize;
float timingOffset = peakAge * Runner.DeltaTime;
bool  isPerfect    = timingOffset <= spike.perfectWindow;

// Power: linear ramp from base→maxNonPerfectSpeed over [0, effectiveFlickPeak].
// Two stacking bonuses on top:
//   • perfectPowerBonus (×~1.12) for perfect FLICK timing
//   • peakJumpBonus     (+~0.25) for contact in the JUMP-peak window
// Combined max ~1.40× — sized so a hard-perfect-peak hit reaches maxBallSpeed exactly.
float effectiveFlickPeak = spike.useAdaptiveFlickReference ? _calibratedFlickPeak : spike.flickPeakReference;
float t     = Mathf.Clamp01(peakMag / Mathf.Max(1f, effectiveFlickPeak));
float power = spike.baseSpikeVelocity + (spike.maxNonPerfectSpeed - spike.baseSpikeVelocity) * t;
if (isPerfect) power *= spike.perfectPowerBonus;
if (phaseAtContact == JumpPhase.Peak && spike.peakJumpBonus > 0f) power *= (1f + spike.peakJumpBonus);
power = Mathf.Min(power, spike.maxBallSpeed);

A player gets one swing attempt per jump — a whiffed spike can't be retried mid-air, which is what makes whiffs both meaningful and funny. Hit types are readable after the fact, too: tips render a purple trail and bounce marks, spikes a distinct trail and red marks, so spectators can decode what happened from the court.

07 AI

A Bot Is Just a Second Producer of Input

A 2v2 game needs four simultaneous players to test, and a solo dev has one. Rather than wait on friends' availability, I built full AI players — and the architecture is the story. The entire AI integration is a single branch at the one point where input enters the simulation. Bots and humans share every downstream system, with zero duplication.

08 AI Difficulty

Difficulty Degrades Perception, Never Buffs Physics

Skill levels are modeled as human-shaped flaws, not stat boosts. A reaction timer restarts whenever the ball's trajectory changes; Gaussian landing-prediction noise shrinks as the ball approaches, so reads resolve late, like a human; and a re-read cadence makes stale targets visibly persist. A Rookie looks late and loose; a Pro looks tight. Both obey identical movement physics.

    trueLand.x + (float)Gaussian() * sigma,

09 AI Cooperation

Reading a Human Teammate's Intent

A human can't broadcast “I've got it,” so the bot reads the same signals a human teammate would: proximity to the predicted contact, velocity toward it, replicated body state (someone in bump stance is committing), and facing. Human and AI partners arbitrate “who takes the ball” through one shared confidence interface.

C# Assets/Scripts/Player/AI/TeammateModel.cs · ~L70 
public override float ClaimConfidence(TeammateContext ctx) {
    // proximity: 1 when on top of the predicted contact, →0 at humanProximityRadius
    float prox = Mathf.Clamp01(1f - dist / Mathf.Max(0.5f, _cfg.humanProximityRadius));
    // approach: moving toward the contact (m/s along dir, ~4 m/s = full)
    float approach = Mathf.Clamp01(Vector3.Dot(vel, dir) / 4f);
    // state: the highest-signal term — Stance/SetStance = committing, airborne = attacking
    float state = StateScore(Player.CurrentBodyState);
    // facing: yaw aligned toward the ball
    float facing = Mathf.Clamp01(Vector3.Dot(fwd, dir));

    return Mathf.Clamp01(_cfg.humanClaimProximityWeight * prox
                       + _cfg.humanClaimApproachWeight  * approach
                       + _cfg.humanClaimStateWeight     * state
                       + _cfg.humanClaimFacingWeight    * facing);
}
10 AI Attack Planning

Real Projectile Math in the Attack Planner

The spike-drive solver reduces the net-clearance constraint to a closed-form minimum time-of-flight, then bisects time-of-flight on the monotonic fast/flat branch to hit a designer-specified launch speed — so the ball lands at the aim point, in-bounds, as fast as the net allows. The deterministic ball model from the netcode section is exactly what makes this exact prediction possible.

C# Assets/Scripts/Player/AI/BotBrain.cs · ~L618 
// Minimum time-of-flight for a contact→aim parabola to cross the net plane (z=0)
// at >= netTop+margin. Net-plane height grows monotonically with T² → closed-form min T.
float MinTimeToClearNet(Vector3 contact, Vector3 aim, float margin) {
    float g = -Physics.gravity.y;
    float cz = contact.z, az = aim.z, cy = contact.y;
    float k = Mathf.Clamp(Mathf.Abs(az - cz) > 0.01f ? -cz / (az - cz) : 0.5f, 0.05f, 0.95f);
    float netClearY = ResolveNetTopY() + Mathf.Max(0f, margin);
    float rhs = (netClearY / (1f - k) - cy) / (0.5f * g * k);
    return rhs > 0f ? Mathf.Sqrt(rhs) : 0f;
}

Vector3 ComputeSpikeDrive(Vector3 contact, Vector3 aim, float targetSpeed) {
    float g = -Physics.gravity.y;
    float horizDist = new Vector2(aim.x - contact.x, aim.z - contact.z).magnitude;
    float dy = aim.y - contact.y;
    float lo = 0.2f, hi = Mathf.Max(0.3f, config.returnMaxTimeOfFlight);
    for (int i = 0; i < 22; i++) {       // |v0| falls as T grows on this branch → bisect for it
        float mid = 0.5f * (lo + hi);
        float vh  = horizDist / mid;
        float vy  = dy / mid + 0.5f * g * mid;
        if (Mathf.Sqrt(vh * vh + vy * vy) > Mathf.Max(1f, targetSpeed)) lo = mid; else hi = mid;
    }
    float T = Mathf.Clamp(Mathf.Max(hi, MinTimeToClearNet(contact, aim, config.spikeNetClearanceMargin)),
                          0.2f, config.returnMaxTimeOfFlight);
    Vector3 v0 = (aim - contact) / T;
    v0.y += 0.5f * g * T;
    return v0;
}

The bots run a full perception → decision → actuation pipeline: receive, set with lane variety, run an approach into a jump-spike, block with deliberately delayed timing, aim at the open court, and mix spike vs tip based on the defense.

11 Movement

The Volleyball “Plant”

A deliberate physics deviation in service of defense: at the jump moment, a curve-driven fraction of horizontal speed converts into vertical boost. Sprint approaches trade forward momentum for hang time, exactly like a real volleyball plant, so defenders can read the hitter's approach. Mid-air control is deliberately minimal — free air mobility would collapse the read-the-hitter game.

C# Assets/Scripts/Player/VolleyPlayer.cs · ~L1094 
// Approach-momentum jump: convert a fraction of horizontal speed into
// vertical boost (volleyball plant). Curve maps approach speed →
// conversion fraction. Bypasses _kcc.Jump() because we need to modify
// horizontal too, not just bump Y.
float conversionFrac = Mathf.Clamp01(movement.approachToVerticalCurve.Evaluate(approachSpeed));
float verticalBoost  = approachSpeed * conversionFrac * movement.verticalConversionRatio;

Vector3 newHoriz = approachSpeed > 0.01f ? horizontalVel * (1f - conversionFrac) : Vector3.zero;
vel.x = newHoriz.x;
vel.z = newHoriz.z;
vel.y = movement.jumpVelocity + verticalBoost;
_kcc.Velocity = vel;
12 Architecture

Five Hit Types, One Seam

Hit type is derived from player state at the moment of ball contact — never picked from a menu. A layered state machine separates body state from hit-attempt lifecycle from derived intent, so adding a new hit type touches one branch in one method. The comments document a real bug class the design prevents: intent locks at stance entry, so the upward camera motion of a hard bump gesture can't re-derive the wrong intent mid-swing.

C# Assets/Scripts/Player/VolleyPlayer.cs · ~L1813 
HitIntent DeriveHitIntent() {
    BodyState body = CurrentBodyState;
    if (body == BodyState.Blocking) return HitIntent.Block;

    if (body == BodyState.AirborneRising || body == BodyState.AirborneFalling) {
        if (_fireHeldThisTick) return HitIntent.Tip;
        return HitIntent.Spike;
    }
    if (body == BodyState.SetStance) return HitIntent.Set;

    if (body == BodyState.Stance || body == BodyState.Dashing) {
        // Intent is committed at stance entry — look angle at contact moment
        // no longer matters (hysteresis keeps you in Stance through
        // mid-gesture camera pans, e.g. the upward boost-swing motion).
        return HitIntent.Bump;
    }
    return HitIntent.None;   // glancing contact, no intent
}
13 Game Feel

Procedural Feel, Computed From Physics

A bridge layer translates gameplay state directly into bone control on the rigged character. There are no impact animation clips: every contact pushes the hands back along the inverse of the outgoing ball velocity (hard spikes recoil harder), compresses them with a squash factor, and decays both with frame-rate-independent exponential lerps. Feel is computed from the same physics values that drive the ball.

C# Assets/Scripts/Player/VolleyPlayerVisuals.cs · ~L276 
void OnLocalHitFromPlayer(Vector3 outgoingVel) {
    float speed     = outgoingVel.magnitude;
    float magnitude = Mathf.Min(speed * impactPushPerMps, impactMaxDistance);
    _impactOffsetR  = -outgoingVel.normalized * magnitude;
    _impactOffsetL  = _impactOffsetR;
    _impactSquashR  = 1f;
    _impactSquashL  = 1f;
    _headImpactIntensity = Mathf.Min(_headImpactIntensity + speed * headImpactIntensityPerMps, 1f);
}

It also contains a fix for a subtle Unity Animator footgun: an additive read-modify-write on a bone compounds forever when the active clip has no keyframes for that bone, because the Animator never resets it. The fix is to always compose smoothedBaseline * offset and never read the bone back.

C# Assets/Scripts/Player/VolleyPlayerVisuals.cs · ~L335 
// Apply impact tilt as a multiplicative offset on top of the smoothed pose.
// Always writes from `_smoothedHeadRot * tiltQuat` — no read of bone state,
// so no compounding regardless of whether the animator wrote the bone.
float impactTilt = -headImpactTiltDegrees * _headImpactIntensity;
_headBone.localRotation = _smoothedHeadRot * Quaternion.Euler(impactTilt, 0f, 0f);

Hit feedback is also a multi-layer audio system: a swoosh on the swing (whiffs included), a thump on every contact, and a slap layered on top only for perfect-timing contact — a perfect hit is audible before it's visible.

14 Tooling

Built for a One-Person Feel-Tuning Loop

Tuning a game by feel, solo, demands fast iteration tooling. So I built it:

  • In-editor telemetry window (a custom EditorWindow): a scrolling 5-second swing-magnitude graph with ~2 minutes of buffered history, calibration reference lines, airborne-shaded regions, color-coded event markers (jump / land / swoosh / perfect / soft / rejected / whiff), and a clickable event list that locks and centers the graph on any past event. All #if UNITY_EDITOR-gated — zero runtime cost in builds.
  • Two ball-machine test rigs: a SettingMachine that feeds sets to you (3 set types × 3 targets, parabola math with controllable apex, scene-view trajectory gizmos) and a HittingMachine that spikes balls at you for receive practice.
  • Tutorial system with a notable design call: slow-motion ball, not slow-motion time — scaling Time.timeScale would also slow the player's arm and break muscle-memory transfer, so only the ball's effective gravity and launch velocity scale while player input runs at full speed.
  • All tuning lives in ScriptableObject configs (SpikeConfig, TipConfig, BumpConfig, MovementConfig, BotConfig, NetConfig…), read every tick so values can be dragged during Play mode. A/B testing is swapping an asset reference on the prefab.
15 Process

Production Discipline Under a Hard Deadline

The engineering is only half of why this is a portfolio piece. The other half is shipping it on a self-imposed six-week clock without the systems collapsing into chaos.

Week 1 spike-feel kill-gate — passed Week 3 networking gate — passed ~4 days tracked buffer
  • A design document treated as the binding spec — when code and doc disagree, the doc wins.
  • A kill-gate at Week 1: if the core swing didn't feel good to an external playtester, the project pauses. It passed.
  • A risk register with named risks (spike feel, networking overrun, Steam lobby bridge, burnout) and per-risk mitigations. Networking risk was front-loaded into Week 3 with a hard gate — two clients, a full rally, no desync — passed on schedule.
  • A written out-of-scope list (cosmetics, ranked, host migration, localization…) to prevent scope negotiation at 11pm, and a strict implementation order that front-loads risk: hardest mechanic first, networking before polish.
